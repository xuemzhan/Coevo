# 分布式任务管理具身智能体系统

# `.agent`任务包协议规范

## 一、协议目的

`.agent`任务包用于在受控网络、物理隔离或无实时连接的环境中，安全传递：

* 项目和任务状态；
* 任务下发要求；
* 任务流程上下文；
* 本地编排计划；
* 文档模板；
* 进展和成果；
* 风险及问题；
* 任务变更；
* 会议决策；
* 审计关联信息。

`.agent`协议解决以下问题：

1. 发送方和接收方身份确认；
2. 数据机密性；
3. 数据完整性；
4. 发送方不可抵赖性；
5. 接收人绑定；
6. 重复包和重放检测；
7. 项目版本冲突识别；
8. 协议和客户端兼容性；
9. 原子导入和失败回滚；
10. 全过程审计关联。

---

## 二、协议适用范围

本协议适用于：

* 任务/项目负责人向成员下发任务；
* 成员向负责人回传进展和成果；
* 任务变更下发；
* 会议决策下发；
* 风险、督办和整改事项传递；
* 离线编排计划传递。

本协议不替代单位既有的信息导入导出、移动介质和保密审批制度。

即使任务包已经加密，仍必须遵守实际环境中的介质、网络和信息流转要求。

---

## 三、术语

### 3.1 任务包

按照本协议封装、加密和签名的`.agent`文件。

### 3.2 外层信封

任务包中可在解密前读取的最小必要协议和路由信息。

### 3.3 内层载荷

经过加密的任务状态、清单、签名、附件和指令。

### 3.4 项目主版本

由任务/项目实际负责人侧维护的项目权威版本。

### 3.5 基线版本

接收方或提交方生成任务包时所依据的项目版本。

### 3.6 包序号

同一发送方针对同一项目和任务生成任务包的递增序号。

### 3.7 重放

同一任务包被再次导入，或旧任务包被重新用于改变当前项目状态。

---

## 四、设计原则

1. 一包一身份；
2. 一包一接收方；
3. 先验证，后导入；
4. 先隔离，后释放；
5. 项目版本优先于时间戳；
6. 明确区分包类型；
7. 所有正式状态变更需人工确认；
8. 导入过程必须原子化；
9. 原始任务包不得被覆盖；
10. 协议版本必须显式声明；
11. 密码套件必须可识别和可升级；
12. 未知字段应按照版本兼容策略处理。

---

## 五、任务包类型

协议定义以下基础包类型。

| 类型标识                 | 中文名称   | 主要用途           |
| -------------------- | ------ | -------------- |
| `TASK_ASSIGNMENT`    | 任务下发包  | 下发任务、角色、流程和模板  |
| `TASK_PROGRESS`      | 进展汇报包  | 回传任务进展和问题      |
| `RESULT_SUBMISSION`  | 成果提交包  | 回传阶段成果或正式成果    |
| `TASK_CHANGE`        | 任务变更包  | 调整计划、责任、范围或交付物 |
| `MEETING_DECISION`   | 会议决策包  | 下发会议决策和责任事项    |
| `RISK_NOTICE`        | 风险通知包  | 传递已确认风险和处置要求   |
| `SUPERVISION_NOTICE` | 督办包    | 传递正式督办事项       |
| `CORRECTION_PACKAGE` | 更正包    | 更正已发送任务包中的错误   |
| `REVOCATION_PACKAGE` | 撤销包    | 撤销尚未生效或需停止执行的包 |
| `AUDIT_CHECKPOINT`   | 审计检查点包 | 传递审计摘要和签名检查点   |

扩展包类型必须使用独立命名空间，不得与基础类型冲突。

## 六、文件命名

建议文件名：

```text
<package_type>_<project_id>_<package_id>.agent
```

示例：

```text
TASK_ASSIGNMENT_PRJ001_7f42c9d0.agent
```

文件名仅用于人员识别，不作为安全和唯一性判断依据。

系统必须以包内`package_id`和签名内容为准。

## 七、物理封装结构

`.agent`文件由以下部分组成：

```text
+----------------------------+
| Fixed Header               |
+----------------------------+
| Envelope Header            |
+----------------------------+
| Encrypted Session Key      |
+----------------------------+
| Encrypted Inner Payload    |
+----------------------------+
| Optional Transport Trailer |
+----------------------------+
```

### 7.1 Fixed Header

固定包头用于快速识别文件和获取长度信息。

协议1.0固定字段（总长度36字节）：

| 字段               |   长度 | 说明            |
| ---------------- | ---: | ------------- |
| Magic            |  8字节 | 固定值`AGENTPKG` |
| Major Version    |  2字节 | 主版本           |
| Minor Version    |  2字节 | 次版本           |
| Header Length    |  4字节 | 外层信封长度        |
| Key Block Length |  4字节 | 密钥块长度         |
| Payload Length   |  8字节 | 密文载荷长度        |
| Flags            |  4字节 | 压缩、扩展等标识      |
| Reserved         |  4字节 | 保留，必须全部置零     |

所有多字节整数统一采用网络字节序（大端）。`Flags`位注册如下：

| 位掩码 | 名称 | 语义 |
| ---: | --- | --- |
| `0x00000001` | `COMPRESSION_ZIP_DEFLATE` | 内层载荷使用ZIP-DEFLATE压缩 |
| `0x00000002` | `EXTENSION_PRESENT` | 存在协议扩展段 |
| `0x00000004` | `KEY_BLOCK_PRESENT` | 存在接收方会话密钥块 |
| `0x00000008` | `PAYLOAD_PRESENT` | 存在密文载荷 |

协议1.0接收端必须拒绝未知标志位。标志位必须与对应长度双向一致：

* `KEY_BLOCK_PRESENT`当且仅当`Key Block Length > 0`；
* `PAYLOAD_PRESENT`当且仅当`Payload Length > 0`；
* 非空密文载荷必须同时携带非空接收方密钥块；
* 不得在没有密文载荷时单独携带接收方密钥块。

协议1.0当前不实现`Optional Transport Trailer`，因此文件精确总长度必须等于`36 + Header Length + Key Block Length + Payload Length`。实现不得把尾随字节静默视为合法扩展。

### 7.2 Envelope Header

外层信封采用规范化UTF-8 JSON，仅包含解密前完成路由和安全判断所需的最小信息。

建议字段：

```json
{
  "protocol_version": "1.0",
  "package_id": "uuid",
  "package_type": "TASK_ASSIGNMENT",
  "sender_cert_id": "CERT-SENDER-001",
  "recipient_cert_id": "CERT-RECIPIENT-021",
  "project_id": "PRJ001",
  "created_at": "2026-07-15T10:20:30+08:00",
  "expires_at": "2026-08-15T23:59:59+08:00",
  "sequence_no": 12,
  "cipher_suite": "CS-SM2-SM4-AEAD-SM3-01",
  "compression": "ZIP-DEFLATE",
  "nonce": "base64",
  "key_block_format": "SM2-KEY-TRANSPORT-V1",
  "payload_length": 123456,
  "required_client_version": "1.0.0"
}
```

外层信封不得包含不必要的任务敏感内容。

外层信封应作为认证加密的附加认证数据，防止其被篡改后仍被系统接受。

### 7.3 Encrypted Session Key

每个任务包生成独立的SM4会话密钥。

会话密钥使用接收方SM2公钥进行封装。

密钥块至少应包含：

* 密码套件标识；
* 接收方证书编号；
* 被封装会话密钥；
* 密钥封装版本；
* 必要的算法参数。

### 7.4 Encrypted Inner Payload

内层载荷应整体采用SM4认证加密模式加密。

正式模式以批准的密码方案和密码模块为准。

不得使用不具备完整性保护的单纯ECB模式。若采用非认证加密模式，必须增加独立的完整性认证机制并经过安全评审。

## 八、内层载荷结构

解密后的内层载荷建议采用标准归档格式，结构如下：

```text
/
├─ manifest.json
├─ signatures/
│  └─ sender.sig
├─ schemas/
│  └─ payload.schema.json
├─ state/
│  ├─ project.json
│  ├─ tasks.json
│  ├─ risks.json
│  └─ workflow.json
├─ payload/
│  ├─ documents/
│  ├─ templates/
│  ├─ results/
│  └─ evidence/
└─ metadata/
   └─ provenance.json
```

内层可以使用标准压缩归档，但必须封装于本协议的加密信封中。

不得将普通ZIP文件直接修改后缀后作为`.agent`任务包。

## 九、Manifest规范

`manifest.json`是任务包的核心清单和签名对象。

### 9.1 基础字段

```json
{
  "protocol_version": "1.0",
  "schema_version": "1.0",
  "package_id": "uuid",
  "package_type": "TASK_ASSIGNMENT",
  "project_id": "PRJ001",
  "task_ids": ["TASK-001", "TASK-002"],
  "sender": {
    "user_id": "USR001",
    "client_id": "CLI001",
    "organization_id": "ORG001",
    "cert_id": "CERT-SENDER-001"
  },
  "recipient": {
    "user_id": "USR021",
    "client_id": "CLI021",
    "organization_id": "ORG002",
    "cert_id": "CERT-RECIPIENT-021"
  },
  "created_at": "2026-07-15T10:20:30+08:00",
  "expires_at": "2026-08-15T23:59:59+08:00",
  "sequence_no": 12,
  "base_revision": "PRJ001-R0008",
  "proposed_revision": null,
  "classification": "INTERNAL",
  "required_client_version": "1.0.0",
  "files": [],
  "requested_actions": [],
  "extensions": {}
}
```

### 9.2 文件清单

每个文件必须登记：

```json
{
  "path": "payload/documents/task_spec.docx",
  "role": "TASK_DOCUMENT",
  "media_type": "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
  "size": 245760,
  "sm3": "hex-encoded-digest",
  "classification": "INTERNAL",
  "required": true,
  "executable": false
}
```

### 9.3 请求动作

任务包可以携带待执行动作，但必须明确权限和确认要求：

```json
{
  "action_id": "ACT001",
  "action_type": "CREATE_WORKSPACE",
  "target_task_id": "TASK-001",
  "requires_confirmation": true,
  "parameters": {
    "workspace_template": "STANDARD-RD"
  }
}
```

任务包不得包含允许任意执行操作系统命令的动作类型。

## 十、JSON规范化

参与签名的JSON必须采用统一规范化规则。

至少包括：

1. UTF-8编码；
2. 不使用BOM；
3. 对象键按字典序排列；
4. 删除无意义空格和换行，规范化字节序列末尾不得附加LF、CRLF或其他空白；
5. 字符串采用统一转义方式；
6. 整数使用十进制且不得有前导零；
7. 签名字段中不使用非确定性浮点数；
8. 百分比建议使用整数基点或整数百分数；
9. 日期时间使用带时区的统一格式；
10. 禁止重复键。

发送方和接收方必须使用同一规范化算法，否则验签结果无效。

## 十一、密码套件

### 11.1 基线套件

协议基线密码套件标识：

```text
CS-SM2-SM4-AEAD-SM3-01
```

含义：

* SM2：接收方会话密钥封装；
* SM2：发送方数字签名；
* SM3：文件和清单摘要；
* SM4认证加密模式：内层载荷机密性和完整性保护；
* 密码学安全随机数：生成会话密钥和Nonce。

### 11.2 正式环境

具体SM4工作模式、随机数源、密钥长度、签名编码、证书格式和密码模块，应以批准的密码应用方案为准。

协议必须通过`cipher_suite`字段明确声明实际采用的密码套件。

### 11.3 禁止事项

禁止：

* 重复使用会话密钥和Nonce组合；
* 使用固定密钥；
* 使用时间戳生成密钥；
* 明文传输会话密钥；
* 将私钥放入任务包；
* 以普通文件摘要替代数字签名；
* 在验签前信任包内业务数据。

---

## 十二、签名范围

发送方必须对规范化后的`manifest.json`及文件摘要集合进行SM2数字签名。

签名对象至少覆盖：

* 协议版本；
* 包编号；
* 包类型；
* 项目编号；
* 任务编号；
* 发送方；
* 接收方；
* 创建时间；
* 包序号；
* 基线版本；
* 数据密级；
* 文件路径；
* 文件大小；
* 文件SM3摘要；
* 请求动作；
* 客户端最低版本。

`sender.sig`建议包含：

```json
{
  "algorithm": "SM2-SM3",
  "signer_cert_id": "CERT-SENDER-001",
  "signed_object": "manifest.json",
  "manifest_sm3": "hex",
  "signature": "base64",
  "signed_at": "2026-07-15T10:20:31+08:00"
}
```

## 十三、任务包生成流程

发送端必须按照以下顺序生成任务包：

1. 校验发送方身份和权限；
2. 确定唯一接收方；
3. 确定项目主版本和任务范围；
4. 生成全局唯一`package_id`；
5. 生成递增`sequence_no`；
6. 生成任务状态和附件；
7. 对每个文件计算SM3摘要；
8. 生成`manifest.json`；
9. 规范化Manifest；
10. 使用发送方SM2私钥签名；
11. 将Manifest、签名、状态和附件形成内层归档；
12. 检查文件类型、数量和总大小；
13. 生成随机SM4会话密钥和Nonce；
14. 对内层载荷进行认证加密；
15. 使用接收方SM2公钥封装会话密钥；
16. 生成外层信封；
17. 写入固定包头和各数据块；
18. 计算最终任务包摘要；
19. 写入导出审计记录；
20. 保存原始发送副本。

生成失败时不得留下可被误发送的不完整任务包。

---

## 十四、任务包导入流程

接收端必须按照以下顺序处理：

1. 将文件放入安全隔离区；
2. 读取固定包头；
3. 检查Magic和协议版本；
4. 检查包长、头长和密钥块长度；
5. 检查包是否超过大小限制；
6. 读取外层信封；
7. 校验接收方身份；
8. 检查客户端最低版本；
9. 检查`package_id`是否已处理；
10. 检查包序号和重放风险；
11. 根据可信时间策略检查有效期；
12. 使用本地SM2私钥解封会话密钥；
13. 使用SM4解密并校验认证标签；
14. 读取内层Manifest；
15. 校验发送方证书和信任状态；
16. 验证SM2数字签名；
17. 校验每个文件的SM3摘要；
18. 检查归档路径和文件类型；
19. 检查压缩比例和解包后大小；
20. 检查包类型和业务权限；
21. 比较项目基线版本；
22. 生成导入预览；
23. 用户确认；
24. 原子创建或更新工作区；
25. 保存原始任务包；
26. 写入审计记录。

任何关键校验失败，任务包均不得进入正式工作区。

---

## 十五、原子导入

任务包导入必须具有事务性。

建议流程：

1. 在临时目录解密和检查；
2. 建立待提交工作区；
3. 完成全部文件写入；
4. 完成数据库状态准备；
5. 执行最终提交；
6. 提交成功后切换为正式状态；
7. 删除临时数据。

如任一步骤失败，应：

* 回滚数据库状态；
* 删除不完整工作区；
* 保留原始任务包；
* 记录错误；
* 将任务包保持在隔离区。

## 十六、项目版本与冲突规则

### 16.1 主版本

项目主状态版本建议格式：

```text
<project_id>-R<revision_number>
```

示例：

```text
PRJ001-R0008
```

### 16.2 汇报包

进展和成果包必须携带生成时引用的`base_revision`。

### 16.3 合并判断

接收端应比较：

```text
package.base_revision
current_project.revision
```

若一致，可进入正常审核。

若不一致，必须进入差异和冲突审核。

### 16.4 冲突展示

至少展示：

* 原基线值；
* 当前主版本值；
* 提交值；
* 提交人；
* 变更字段；
* 证据文件；
* 包编号。

### 16.5 处理方式

审核人可选择：

* 接受提交值；
* 保留当前值；
* 手工修改；
* 部分合并；
* 暂不合并；
* 退回提交人。

不得提供“覆盖全部项目状态”的默认操作。

### 16.6 合并结果

合并成功后必须：

* 生成新项目主版本；
* 记录合并人；
* 关联原始任务包；
* 保存冲突处理记录；
* 支持按权限撤销；
* 防止同一包再次生效。

---

## 十七、重放和重复包控制

系统必须维护已处理包登记表，至少记录：

* `package_id`；
* 包类型；
* 发送方；
* 接收方；
* 项目编号；
* 包序号；
* 处理时间；
* 处理结果；
* 对应项目版本；
* 原始文件摘要。

以下情况应被识别：

1. 相同`package_id`再次导入；
2. 相同包摘要再次导入；
3. 包序号明显早于已处理序号；
4. 已撤销包再次导入；
5. 更正包引用不存在的原包；
6. 同一成果包尝试重复更新项目状态。

重复包原则上不得再次执行，但可允许安全管理员查看历史处理结果。

---

## 十八、可信时间和有效期

任务包可包含创建时间和失效时间，但离线终端不得仅依赖本地系统时间作出安全判断。

有效性判断应综合：

* 本地可信时间状态；
* 最近一次签名时间基准；
* 包序号；
* 项目版本；
* 证书状态；
* 任务包撤销信息。

如终端时间异常，应：

* 生成告警；
* 限制依赖时间的自动处理；
* 转入人工审核；
* 不得直接以本地时间判定包绝对有效。

---

## 十九、文件安全规则

### 19.1 路径

包内路径必须为相对路径。

禁止：

* 绝对路径；
* `..`路径跳转；
* 设备路径；
* 网络共享路径；
* 盘符路径；
* 符号链接指向包外位置。

### 19.2 文件类型

允许文件类型应由策略配置。

默认应禁止：

* `.exe`；
* `.dll`；
* `.bat`；
* `.cmd`；
* `.ps1`；
* `.vbs`；
* `.msi`；
* `.com`；
* `.scr`；
* 其他可执行或脚本类型。

带宏文档应按照单位策略拒绝或进入专门审查。

### 19.3 容量限制

协议实现应配置：

* 最大任务包大小；
* 最大文件数量；
* 最大单文件大小；
* 最大解包后体积；
* 最大压缩比例；
* 最大目录深度；
* 最大路径长度。

超过限制时不得继续自动解包。

### 19.4 嵌套归档

MVP原则上禁止任务包中包含多层嵌套压缩文件。

确需传输时，应经过人工安全审批。

---

## 二十、协议版本管理

### 20.1 版本格式

协议版本采用：

```text
major.minor
```

### 20.2 主版本

主版本变化表示存在不兼容调整。

客户端不得强制解析未知主版本。

### 20.3 次版本

次版本可增加可选字段。

接收端应忽略其明确允许忽略的未知可选字段，但不得忽略未知的安全关键字段。

### 20.4 Schema版本

业务数据结构版本与协议版本分别管理。

Manifest必须声明：

* `protocol_version`；
* `schema_version`；
* `required_client_version`。

---

## 二十一、扩展字段

扩展字段统一放入`extensions`对象，并使用组织或产品命名空间，例如：

```json
{
  "extensions": {
    "kaiwu.workflow.priority": "HIGH",
    "org001.custom_stage": "STAGE-A"
  }
}
```

扩展字段不得改变基础协议的身份、签名、加密、版本和权限语义。

| `AGT-CRY-004`  | 文件摘要不匹配  |
| `AGT-RPL-001`  | 重复任务包    |

## 二十三、审计要求

任务包相关审计至少包括：

* 生成；
* 导出；
* 导入；
* 隔离；
* 解密；
* 验签；
* 摘要校验；
* 重复检测；
* 基线冲突；
* 用户确认；
* 工作区初始化；
* 状态合并；
* 撤销；
* 删除；
* 异常处置。

审计记录必须关联：

* 包编号；
* 包摘要；
* 项目编号；
* 任务编号；
* 发送方；
* 接收方；
* 客户端；
* 操作结果；
* 错误码；
* 项目版本。

## 二十四、任务包保留

发送端和接收端均应保留原始任务包。

不得在导入、解密或合并后覆盖原始文件。

归档应至少包含：

* 原始加密包；
* 最终包摘要；
* 导入或导出记录；
* 签名验证结果；
* 对应项目版本；
* 合并结果；
* 撤销或更正关系。

保留周期根据项目档案和安全管理要求确定。

---

## 二十五、更正和撤销

### 25.1 更正包

更正包必须引用：

* 原任务包编号；
* 原包摘要；
* 更正原因；
* 受影响字段；
* 新的基线版本。

### 25.2 撤销包

撤销包必须引用被撤销包，并明确：

* 撤销原因；
* 撤销范围；
* 是否停止执行；
* 是否需要回滚；
* 审批人。

已完成并正式验收的任务不得仅通过普通撤销包直接删除历史记录。

* 原子导入；
* 文件安全检查；
