# 分布式任务管理具身智能体系统MVP版本用户故事

## 一、MVP目标

MVP用于验证以下三类核心能力：

1. **任务管理智能能力**：任务流程理解、任务分解、进展采集、风险预警、督办、简报和成果沉淀。
2. **分布式离线协同能力**：任务包能够安全下发、本地执行、成果回传、冲突审核和版本合并。
3. **运行中枢编排能力**：能够根据任务事件动态调用专业子智能体、智能任务协同会议智能体和“开悟”本地工具。

---

## US-0：【身份与信任】离线用户身份和密钥初始化

### 用户故事

作为系统安全管理员，我想为任务/项目负责人和任务成员配置可信身份、项目角色、证书及加解密密钥，以便系统在离线条件下识别发送方和接收方，并安全完成任务包流转。

### 验收标准

1. 支持导入用户身份、所属单位和项目角色；
2. 支持导入可信证书、公钥和本地私钥；
3. 私钥不得以明文方式保存；
4. 支持密钥编号、有效期和撤销状态检查；
5. 身份应与任务权限和项目角色关联；
6. 身份和密钥配置操作形成审计记录。

---

## US-1：【任务流程理解】不同单位任务流程解析与映射

### 用户故事

作为任务/项目实际负责人，我想导入任务承担单位的流程资料，由任务流程理解智能体提取阶段、节点、角色、输入输出和评审要求，以便在不强行统一各单位流程的情况下建立可协同的流程模型。

### 验收标准

1. 支持导入流程文档、表格或已有流程模板；
2. 自动提取阶段、节点、角色、输入、输出和评审要求；
3. 展示原始资料与解析结果的对应关系；
4. 标识模型提取字段的来源和置信度；
5. 用户可以人工修改解析结果；
6. 确认后形成带版本号的单位任务流程模型；
7. 支持将单位流程节点映射到系统统一任务阶段。

---

## US-2：【任务分解】基于流程模型形成结构化任务

### 用户故事

作为任务/项目实际负责人，我想根据任务目标和适用流程自动形成任务结构，以便快速建立可执行、可跟踪和可验收的任务计划。

### 验收标准

1. 用户可录入任务名称、目标、起止时间和承担单位；
2. 系统可选择已经确认的任务流程模型；
3. 任务分解智能体自动生成阶段、工作包、任务和里程碑；
4. 每项任务包含交付物、责任角色、计划时间和验收标准；
5. 自动识别前置依赖和输入输出关系；
6. 用户可新增、删除、修改或重新排序任务；
7. 人工确认后形成项目初始基线版本。

## US-3：【团队组建】基于脱敏人才库推荐任务成员

### 用户故事

作为任务/项目实际负责人，我想基于本地脱敏人才库获得候选人员建议，以便快速、科学地完成项目初始组队，同时保护人员隐私和敏感信息。

### 验收标准

1. 系统能够读取本地脱敏人才数据库；
2. 数据至少包含人员代号、技术标签、资质、当前任务数和可用时间；
3. 系统按照任务类型推荐候选人员；
4. 展示候选人的匹配度和推荐理由；
5. 识别人员负荷过高和任务时间冲突；
6. 用户可手工替换推荐人员；
7. 用户确认后形成任务责任分工；
8. 人员调整过程形成操作记录。

## US-4：【运行中枢】子智能体注册与最小任务编排

### 用户故事

作为任务/项目实际负责人，我想让运行中枢根据任务阶段和状态变化，调用适当的专业子智能体，以便不同智能体围绕同一任务目标协同工作。

### 验收标准

1. 七类专业子智能体能够登记名称、能力、输入和输出要求；
2. 运行中枢显示子智能体可用状态；
3. 能够根据任务事件触发预设编排流程；
4. 界面显示当前步骤、调用对象和执行结果；
5. 高影响操作具有人工确认节点；
6. 调用失败时支持重试、跳过或转人工；
7. 编排过程形成审计记录。

### MVP固定编排链

> 任务输入 → 任务流程理解 → 任务分解 → 团队推荐 → 负责人确认 → 生成任务包。

## US-5：【任务下发】加密任务包生成与导出

### 用户故事

作为任务/项目实际负责人，我想将确认后的任务、角色、流程上下文和文档模板生成接收人专属加密任务包，以便在物理隔离环境中安全下发任务。

### 验收标准

1. 项目和任务状态能够转换为标准JSON；
2. 任务包包含项目编号、任务编号、发送人、接收人、包类型和基线版本；
3. 包含任务描述、流程要求、交付物要求和WPS模板；
4. 多个接收人分别生成接收人专属任务包；
5. 任务包内容采用SM4加密；
6. SM4密钥使用接收方SM2公钥封装；
7. 包清单和关键元数据使用发送方SM2数字签名；
8. 用户可通过本地保存对话框导出`.agent`文件；
9. 任务包不得包含接收方无权访问的数据。

## US-6：【工作区初始化】离线任务包导入和本地空间创建

### 用户故事

作为任务成员，我想将收到的`.agent`任务包导入本地客户端，由系统完成安全检查和角色工作区初始化，以便在完全离线环境中开始工作。

### 验收标准

1. 支持目录监听和手动选择两种导入方式；
2. 导入包首先进入安全隔离区；
3. 系统检查接收人、完整性、数字签名、有效期和重复包；
4. 异常包不得释放到正式工作区；
5. 成功导入后创建独立项目和角色目录；
6. 释放任务描述、流程要求、交付物要求和文档模板；
7. 初始化失败时不得留下不完整工作区；
8. 同一任务包重复导入时不得重复创建任务。

5. 左侧导航列出本地全部项目和角色；
6. 点击项目或角色可切换独立工作视图；
7. 用户可查看任务、里程碑、交付物和当前状态；

## US-8：【进展采集】本地任务状态和成果证据识别

### 用户故事

作为任务成员，我想让进展采集智能体从本地工作文档、任务反馈和成果文件中识别进展变化，以便减少重复填报并生成可核验的汇报内容。

2. 提取已完成工作、未完成工作、下一步计划和存在问题；
3. 每项进展关联相应成果证据；
4. 显示信息来源和置信度；
5. 用户可以修改或驳回识别结果；
6. 正式任务状态必须由用户确认；

## US-9：【成果回传】成果汇报包生成

### 用户故事

作为任务成员，我想在完成阶段工作后生成成果汇报包，以便将任务状态和成果安全提交给任务/项目实际负责人。

3. 携带项目编号、任务编号和原始基线版本；
4. 携带包唯一编号和提交序号；
5. 采用与任务下发包一致的加密和签名机制；
6. 用户确认后生成`Report.agent`文件；
7. 原始成果文件保留在本地工作区；
8. 导出操作形成审计记录。

## US-10：【状态合并】成果包审核和项目主版本更新

### 用户故事

作为任务/项目实际负责人，我想审核成员提交的成果汇报包，并按照任务和字段进行差异合并，以便在多人离线协同时维护准确的项目权威状态。

### 验收标准

1. 系统校验成果包身份、签名、完整性和基线版本；
2. 重复汇报包不得重复生效；
3. 对比成员引用基线和当前项目主版本；
4. 无冲突内容进入正常审核；
5. 有冲突内容展示原基线值、本地值和提交值；
6. 用户可选择接受提交值、保留本地值、手工调整、暂不合并或退回；
7. 不得仅依据时间戳进行强制覆盖；
8. 合并后生成新的项目主版本；
9. 原始汇报包和合并记录永久保留；
10. 已合并结果支持按权限撤销。

## US-11：【风险预警】基于项目状态识别任务风险

作为任务/项目实际负责人，我想让风险预警智能体分析合并后的任务进展、依赖关系和成果证据，以便提前发现延期、资源冲突、接口问题和条件不足。

### 验收标准

3. 每项风险显示判断依据和影响任务；

6. 识别风险对关联任务的影响；
7. 重大风险可建议召开任务协同会议；
8. 风险正式发布前由负责人确认。

8. 会议结论转化为任务、风险处置或督办事项；

## US-15：【安全审计】异常包拦截和全过程留痕

作为系统安全管理员，我想对身份认证、任务包流转、智能体调用、项目状态合并和异常操作进行统一审计，以便满足安全保密和责任追溯要求。

6. 安全管理员能够查询和导出审计日志；
7. 异常任务包不得导致客户端崩溃；

## US-16：【框架层】受控智能体声明校验与策略抽象（CTAF 落地）

### 用户故事

作为受控场景（政府 / 军工 / 金融 / 科研）的安全管理员和框架扩展者，
我想在部署点对智能体声明（Agent Manifest）进行强制校验，并把 Plan 的数值边界
统一收敛到策略模板（Policy），以便只有声明合规、策略受控的智能体才能进入编排，
且 LLM 生成的 Plan 无法越权、绕过人工确认或擅自修改执行边界。

### 验收标准

**AC-1：manifest-checker（CTAF §5.3 / M1a）**

1. 最小合法 Agent Manifest 通过校验并注册（T1）；
2. capability 必须属于 CTAF §5.2 能力闭集，闭集外一律拒绝，不得注册（T2）；
3. `requires_human_confirmation` 缺省为 true，与现有编排步骤语义一致（T3）；
4. `crypto_scope` 必须属于 ProviderScope 闭集，否则拒绝（T4）；
5. `redact_in_audit` 必须是审计投影字段的子集，否则拒绝（T5）；
6. `spec_hash` 必须等于"排除 `spec_hash` 与 `policy_ref.signature` 自指字段后的
   规范化字节"的 SHA-256；无法规范化或哈希不一致时拒绝（F5）；
7. `policy_ref` 三段绑定（spec_hash / signer_cert_fingerprint / SM2 签名）任一
   不匹配即拒绝；验签公钥必须来自证书链，不得取自 `policy_ref` 自身（F8）；
8. `policy_profile` 必须绑定 `policy_version`，无版本引用或与部署点策略注册表
   不一致时拒绝（F7）；
9. 校验失败仅返回 `failure_reason`，不得注册；校验与注册逻辑必须为纯函数、
   可离线运行、零新增三方依赖（L15）；
10. `.agent` v1.0 wire 字节级保持不变，并提供回归测试钉住（T6）。

**AC-2：Policy 抽象与 validate_plan（CTAF §6.5 / M2）**

1. Policy 包含 `policy_id` / `policy_version` / `profile` / `timeout_profile` /
   `retry_profile` / `consent` / `audit_redaction` / `ground_truth_required` 字段，
   `policy_version` 为必填（F7）；
2. 提供 4 个默认 Profile（INTERACTIVE / BATCH / AUDIT_ONLY / EMERGENCY），
   所有 Profile 的 `max_recover_attempts` ≤ 3，对齐 L16 与状态机
   "recover 计数 ≥ 3 → ESCALATED"（F1）；
3. EMERGENCY 采用 fail-fast 语义：1 次重试、总时限 60s、不在线等待人工，
   改为强制审计 + 事后 30 分钟内人工确认，且不依赖外部通知 SaaS（F1 / F9）；
4. Plan 内不得出现策略归属数值键（max_plan_depth / max_runtime_sec /
   max_recover_attempts / timeout 等），数值统一从 Policy 取（L18 白名单口径，F6）；
5. `PlanNode.tool_args` 等数据字段按 schema 允许携带数值，不得被 L18 误拒（F6）；
6. `OrchestrationEngine.validate_plan` 为 dispatch 前置必调：校验 §6.4.1 五项
   不变量 + L18 + L19，失败返回 REJECTED，不得进入 dispatch（A9 / F4）；
7. ESCALATED 状态机不得直跳 ACTIVE，任何回到 ACTIVE 的路径必须经 HELD 中转，
   RETIRED 可直接退出（L19 语义，F4）；
8. Policy / Plan 校验逻辑必须为纯函数、可离线运行、零新增三方依赖，
   新增模块受 `test_module_docs.py` 文档守卫约束（L17）。

**AC-3：能力闭集收敛（CTAF §5.2 / M1b）**

1. 提供框架能力注册表，覆盖 CTAF §5.2 全部能力名称；MVP 能力映射到
   `AgentCapability` 单一事实来源；
2. 支持双名解析：`AgentCapability` 枚举值与 CTAF 规范名解析到同一规范条目；
   闭集外 / 大小写变体一律拒绝；
3. manifest-checker 的 capability 校验切换至框架注册表：MVP 能力必须可映射
   （未登记/未映射的能力明确拒绝）、`CRYPTO_PROXY` 必须
   `crypto_scope=approved-product`、框架抽象能力（PLANNER / ROUTER /
   AGGREGATOR / EVALUATOR / OPTIMIZER / HUMAN_GATE）允许用于 Plan 层；
4. 注册表与既有 `AgentCapability` 双向一致（无孤儿成员、无未映射 MVP 名），
   不一致即测试失败；
5. 纯函数、离线、stdlib、L17 文档守卫。

# 二、MVP实施优先级

## 第一优先级：离线任务协同基本闭环

* US-2 任务分解；
* US-3 团队组建；
* US-5 任务下发；
* US-6 工作区初始化；
* US-7 本地驾驶舱；
* US-8 进展采集；
* US-9 成果回传；
* US-10 状态合并；
* US-15 安全审计。

## 第二优先级：体现智能体系统特征

# 三、MVP演示闭环

1. 导入两个不同单位的任务流程资料；
2. 任务流程理解智能体形成流程模型和映射关系；
3. 任务/项目实际负责人输入一个跨单位任务；
4. 任务分解智能体生成任务、里程碑、交付物和依赖关系；
5. 从本地脱敏人才库推荐项目成员；
6. 负责人确认后形成项目初始基线；
7. 为不同成员生成接收人专属`.agent`任务包；
8. 成员端完成验签、解密和工作区初始化；
9. 成员通过本地驾驶舱和“开悟”工具开展工作；
10. 进展采集智能体识别任务状态和成果证据；
11. 成员确认并生成成果汇报包；
12. 负责人端完成差异审核和版本合并；
13. 风险预警智能体识别任务延期及关联影响；
14. 运行中枢调用决策简报智能体生成风险材料；
15. 负责人确认启动智能任务协同会议；
16. 会议结论转化为新的任务或督办事项；
17. 新任务再次通过任务包下发；
18. 阶段结束后生成复盘报告和知识包；
19. 全过程通过安全审计记录进行追溯。

# 四、MVP验收结论

MVP通过验收应同时满足以下条件：

1. 能够解析不同单位的任务流程；
2. 能够形成结构化任务和项目初始基线；
3. 能够基于脱敏人才库提供团队推荐；
4. 能够安全生成、传输和导入离线任务包；
5. 能够在本地完全离线环境下执行任务；
6. 能够采集任务进展并关联成果证据；
7. 能够基于基线版本审核和合并成果；
8. 能够识别至少一类任务风险；
9. 能够由运行中枢调度至少三类专业子智能体；
10. 能够调用“开悟”工具形成任务材料；
11. 能够形成会议决策转任务的闭环；
12. 能够对关键行为和异常情况进行完整审计。

只有同时形成“业务智能、分布式离线协同、运行中枢编排”三类最小能力，MVP才能证明分布式任务管理具身智能体系统的核心技术和应用模式可行。
