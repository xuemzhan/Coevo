# 离线合并收敛语义（Merge Convergence Contract）

> 状态：生效（2026-08-10，ARCH-REVIEW-2）
> 适用范围：`src/coevo/merge`（MergeEngine / MergeCommitReceipt / MergeReceiptRepository）的状态合并语义。
> 背景：2026-08-10 资深架构师审查要求明确离线合并的"收敛性"——多成员并发提交、部分合并、重放之后主版本是否唯一、过程是否终止、结果是否可复现。

## 1. 合并代数定位

`MergeEngine` **不是可交换/可结合的 CRDT**，也不做字段级自动合并的并发协调。它是
**"串行化 + 冲突停止（fail-closed）"的合并器**：一次 `merge` 只处理一个已通过身份、
完整性与签名校验的结果包，版本推进完全由"当前主版本"线性决定。

## 2. 收敛不变量（P1..P6）

- **P1 确定性重放**：对同一有序输入序列（同一组结果包 + 同一 `decided_at`）执行两次，
  产生字节一致的最终主版本（`canonical_baseline_digest` 相同）与相同的接受/挂起序列。
- **P2 幂等**：同一结果包（相同 `package_id`/摘要）重复合并且已登记时，第二次为
  no-op（`accepted=False`、不升版本、store 不变）。
- **P3 全有或全无**：任一字段决策为 HOLD（含风险字段、陈旧基线冲突）时，整个提案
  `accepted=False`，`new_baseline` 与输入基线完全一致；**不存在部分合并产生的半成品版本**。
- **P4 陈旧基线串行化**：结果包的 `base_revision` 不等于当前主版本时，绝不静默合入——
  产出 HOLD-with-conflict（`accepted=False`、`has_conflict=True`）。并发成员对同一基线的
  提交因此被强制串行化：先到者生效，后到者进入人工审核。
- **P5 版本单调**：每次被接受的合并恰好把主版本 +1（严格单调，且不得跳跃或回退）。
- **P6 收敛定义**：
  - 对同一"已接受序列"重放，最终主版本唯一且可复现（由 P1 保证）；
  - 冲突（并发、陈旧基线、HOLD 字段）不靠自动合并收敛，而是停止推进、交由有权限人员
    裁决（接受/退回/人工合并），之后基于新主版本重新提交，再按 P1-P5 继续；
  - 因此系统的收敛保证是"重放确定性 + 冲突人工裁决后重提"，而非"任意顺序自动收敛"。

## 3. 部分合并语义

"部分合并"在协议层体现为 HOLD-with-conflict 提案：调用方可展示三方值
（original / current / submitted）并选择接受提交值、保留本地值、人工修改、暂不合并或退回。
任何此类处置都发生在**提案之外**，不直接改写主版本；只有重新提交并通过 `merge` 的
结果包才能推进版本。`MergeCommitReceipt` 仅对被接受的合并签发（原子：接受必有收据，
未接受必无收据）。

## 4. 守卫测试

`tests/unit/test_arch_review_2_merge_convergence.py` 以固定种子的伪随机序列验证：

- 同序重放确定性（P1）；
- 重复包幂等 no-op（P2）；
- HOLD 全有或全无（P3）；
- 陈旧基线绝不静默合入（P4）；
- 接受合并恰好 +1（P5）；
- 随机序列（多种子、混合有效/陈旧基线）全程保持 P1-P5。

## 5. 变更纪律

任何修改合并字段规则、版本推进、HOLD/冲突语义或收据签发条件的改动，必须同步更新本契约
并在 `loop/DECISIONS.md` 留痕；删除或放松上述任何一条不变量，视为合并语义变更，
需要架构评审。
